# Trade 从零重构文档

版本：设计基线 1.0 · 实施更新 2026-09-26；当前代码范围见 [实施状态](IMPLEMENTATION_STATUS.md)，实际验收与平台边界见 [发行验收](RELEASE_ACCEPTANCE.md)。

## 1. 要构建什么

构建一个本地优先的个人交易研究与复盘工作台，覆盖 **行情 → 选股 → 策略验证 → 模拟执行 / 真实交易记账 → 资金核对 → 日周月复盘 → 方法沉淀**。

以 final-trade 的工作台布局和青绿色基调为视觉基础，吸收 LaimiuTrade 的交易账本、单位净值、目标节点、结构化复盘、截图识别与灵感卡片。最终为一个前端、一套导航、一套设置和一套受版本管理的数据模型。

仓库保留早期双前端与 iframe 过渡实现。新应用使用独立的 `trade_app`、`rebuild.html` 和 `scripts/run_trade_rebuild.py`；启动与打包按 [新应用发行说明](REBUILD_PACKAGING.md)，实施状态以代码和 [逐功能核对](FEATURE_COMPLETION_AUDIT.md) 为准。

## 2. 已确定的边界

| 项目 | 决定 |
|---|---|
| 产品名 | 暂用 Trade |
| 使用者 | 单人、本地优先；保留服务端部署能力 |
| 界面基础 | final-trade 的桌面工作台；新增完整浅色 / 深色主题 |
| 功能范围 | 两个原项目的有效业务能力全部纳入；原独立研究脚本单独承接 |
| 真实交易 | 手动记账、截图识别后人工确认；当前范围没有券商自动下单 |
| 模拟与回测 | 各自拥有独立执行状态与数据范围，可关联复盘 |
| 旧数据 | 原目录与原数据库保留；新系统从独立空库开始，不自动扫描并迁入旧数据 |
| 数据导入 | 保留 JSON 恢复、报告导入等已有能力；历史数据迁移作为后续用户主动执行的导入工具 |
| AI | 可选能力；可配置文本与视觉模型；无 AI 时手动流程可用 |
| 当前产物 | 独立重构应用、冻结行情与结果、迁移工具、研究 CLI、统一界面及 Windows 本地发行包；跨平台和外部服务验收单列 |

“功能完整”以功能验收与原版本对照为准；原有缺陷应按修正后的行为实现，旧行为如需复现，应显式标注兼容版本。

## 4. 核对基线

| 来源 | 固定提交 | 已提取范围 |
|---|---|---|
| final-trade | `2a00ffe7c50b5f023a5db9f1c09ace1683eb1912` | 109 个显式 HTTP 接口、19 个业务页面和 404 路由、16 个实际注册策略 |
| LaimiuTrade | `0953c1d42fe18e808197d6d06df41f1db5e01c94` | 64 个显式 HTTP 接口、9 个业务页面、账本与复盘数据模型 |
| 当前 Trade | `3de868bc29ef906dddee6d9cc7082cfb1a6898f8` | 过渡整合与前序审查参照 |

173 个接口均已分配功能 ID；这只证明接口已归档。前端本地偏好、导出、交互与脚本也在功能说明中单列，仍需开发时逐项对照。这里没有把 README 中的未来计划当作已实现功能，也没有把被移除的策略定义计入 16 个策略。

清单可用 `python docs/generate_source_inventory.py` 重建，要求两个原仓库仍位于当前仓库的同级目录，且 Python 环境能导入原策略注册器。脚本只读原仓库，写入清单文件；清单含提交号及工作区是否有改动。

## 5. 开发完成的判断

1. F01–F78 各有实现位置、验收记录和已知限制；不得因模块合并删除原功能。
2. 三种数据范围清晰：真实账本、模拟账户、回测实验；用户始终能看见当前范围。
3. 相同数据与相同算法版本可复现结果；有意修正的差异有说明。
4. 记账、保存、备份、恢复、升级和目录迁移通过失败场景验证。
5. 原有导出格式、16 个策略以及独立研究脚本完成兼容验收。
6. 所有业务页面使用统一组件与令牌；浅色、深色、窄屏和打印均可使用。
7. 分阶段交付期间可使用旧版；只有完成全量验收后，才称为两个软件的完整替代品。
